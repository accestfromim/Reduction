Feature 层有环：VoiceLoop → ReplyObserver(chat.ui) → ChatController → SpeechController(voice)。AppGraph 能组装，但 feature 模块并不独立。
功能层只决定“何时做”；模型层只生成文本/PCM；硬件层只采集和播放。当前列的对应关系比跨层箭头更重要。

我会先挑这些毛病

P1 架构
Feature 层循环依赖
VoiceLoop → ReplyObserver(chat.ui) → ChatController → SpeechController(voice)。建议把 ReplyObserver 移到 core 或 voice 的端口接口，ChatController 不再反向依赖 voice。
P1 语义
over 时 trustText=true
TurnListener 在明确 over 时直接用最后一次滚动 ASR，没有最终 ASR。最后 1 秒的词或修正可能丢。要么 over 后补一次最终 ASR，要么把“trust rolling”做成显式策略。
P1 时序
autoSpeak=false 时 followup 不等“好的”
ReplyStreamer 只在有 TTS 时等 ack。关掉自动朗读时，ChatController 立即结束，VoiceLoop 250ms 后开麦，可能把“好的”录进去。onReplyEnded 也应等待 ack。
P1 状态
cancel 后 REPLYING 继续说话
VoiceLoop.cancel 在 REPLYING 时直接回 IDLE，但注释和实现都允许回复继续播放。此时“唯一状态源”已经不再描述正在发生的语音。
P2 时序
cue 超时硬编码 1.5s
“我在/好的”都靠 1.5s 超时兜底。文件稍长或 MediaPlayer 启动慢就会被截断。应根据 duration + margin，或由播放器结束事件唯一推进。
P2 边界
VoiceLoop 直接依赖 AudioOutputHost
判断耳机输出、暂停唤醒都在 VoiceLoop 里；这是 UI/设备策略。可以考虑收进 AudioOutputHost 或一个 BargeInPolicy，让状态机只处理状态。
